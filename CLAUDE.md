# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A local-only, single-user personal finance tracker (Turkish). Core loop: upload an Enpara credit card statement PDF → parse it → auto-categorize transactions → user reviews/corrects → dashboard/analytics. No auth, no multi-user, no cloud — everything runs on `localhost` against a local SQLite file.

Two documents drive all product/architecture decisions and must be consulted before making non-trivial changes:

- **`PROJECT_SPEC.md`** — the full 74-section requirements spec (Turkish). Contains the exact business rules (duplicate-import logic, category priority order, installment math, subscription-detection heuristics, MVP scope boundaries, etc.). When a feature's exact behavior is ambiguous, this is the source of truth.
- **`docs/PHASES.md`** — the living phase-by-phase build tracker (Faz 1–12). Check this first to see what's already built vs. still a placeholder, and read it before starting the next phase — each phase's checklist and "known issues" notes carry context that isn't repeated here.

This project is built incrementally, one "Faz" (phase) at a time, per the user's explicit request — do not jump ahead to a later phase's features without being asked.

npm run typecheck       # tsc --noEmit — see gotcha below
npm run lint

**Gotcha:** `npm run typecheck` depends on generated route types (`.next/types/`), which are gitignored and only produced by `next dev`, `next build`, or `npx next typegen`. On a fresh checkout, run one of those once before `typecheck` will pass — otherwise it fails on `LayoutProps<"/">` / `PageProps<"/route">` not being found.

Run typecheck → lint → test → build after finishing each phase, and don't move to the next phase until all four are clean (this is an explicit project rule, not just good practice — see `PROJECT_SPEC.md` §70).

## Architecture

### Stack specifics that differ from defaults

- **Next.js 16 App Router on Turbopack**, React 19, TypeScript strict. This Next.js version has real breaking changes vs. older training data — `AGENTS.md` (auto-generated by `next dev`, do not remove) points at `node_modules/next/dist/docs/` as the authoritative reference. Page components use the generated `PageProps<'/route'>` / `LayoutProps<'/route'>` helper types (from `.next/types/routes.d.ts`), not hand-written prop types; `searchParams` is a `Promise`.
- **Tailwind v4**, CSS-based config (no `tailwind.config.ts`) — theme tokens live in `app/globals.css` under `@theme inline` + `:root`/`.dark`. The design-token set is `background/surface(card)/border/primary/success/warning/danger/muted/text`, matching `PROJECT_SPEC.md` §43. `success`, `warning`, and `danger` are *not* part of shadcn's default palette — they were added by hand; `danger` aliases `destructive`. If a new semantic color is needed, add it in both `@theme inline` and both `:root`/`.dark` blocks or it silently renders as no color.
- **shadcn/ui is configured on Base UI (`@base-ui/react`), not Radix** (`components.json` → `"style": "base-nova"`). This matters for every interactive primitive in `components/ui/`:
  - Trigger components take a `render={<Element/>}` prop instead of Radix's `asChild` pattern.
  - `Select`'s `<Select.Value>` renders the **raw `value` string**, not the matching item's label, unless the `Select` root is given an `items={{value: label}}` map. Every `Select` usage in this repo passes `items` for this reason — if you add a new one and skip it, the trigger will visibly show raw IDs/enum values instead of labels (this exact bug was hit and fixed once already).
  - React 19's "reset uncontrolled fields after a successful form action" behavior interacts with Base UI's `Input`/`Select` internals and prints a harmless dev-only console warning ("A component is changing the default value state of an uncontrolled FieldControl…") on some edit-then-save flows. It's cosmetic (stripped in production, no functional effect) — don't spend time chasing it further unless it starts affecting behavior.
- **Prisma 7**, which changed its connection model: `datasource.url` is *not* set in `prisma/schema.prisma` anymore. CLI config (migrate/generate/studio) lives in **`prisma7.config.ts`** (that literal filename — not `prisma.config.ts`) and reads `DATABASE_URL` via `dotenv/config`. At runtime, `PrismaClient` requires an explicit driver adapter — see `lib/db/client.ts`: `new PrismaClient({ adapter: new PrismaBetterSqlite3({ url: process.env.DATABASE_URL }) })`. Any standalone script that instantiates `PrismaClient` directly (rather than importing `lib/db/client.ts`) needs the same adapter wiring or it throws `PrismaClientInitializationError`. Prisma's `latest` npm dist-tag currently points at an `8.0.0-rc` prerelease with vulnerable transitive dev-tooling deps — this repo pins `prisma`/`@prisma/client` to the exact stable `7.10.0`; don't let `npm install` float it back to `latest`.
- **`pdf-parse` (and its `pdfjs-dist` dependency) must stay in `next.config.ts`'s `serverExternalPackages`.** Without it, Turbopack bundles `pdfjs-dist` into a server chunk, and its Node worker setup then looks for `pdf.worker.mjs` at a bundled path that doesn't exist on disk, throwing `Setting up fake worker failed` — but *only* when the parser runs through an actual Next.js server request (a Server Action, a route handler). Calling `EnparaParser.parse()` directly from Vitest/Node (as `tests/parser/*.test.ts` does) never hits this, which is exactly why it wasn't caught until Faz 5's `/statements/import` flow was exercised in a real browser. If PDF parsing ever throws this error again, check this config first before touching parser code.

### Money handling

All monetary values are stored and computed as **integer kuruş** (`Int` in Prisma), never floats. `lib/money.ts` is the single place allowed to convert between kuruş and TL strings (`parseTLToKurus`, `kurusToTL`, `formatKurus`) — never parse or format currency ad hoc elsewhere. Turkish number format is thousands-separator `.`, decimal separator `,` (e.g. `"1.250,50 TL"` → `125050`).

### Server Actions / form pattern

Every domain (`transactions`, `income`, `categories`, …) follows the same shape, established in `app/transactions/`, `app/income/`, `app/categories/`:

- `app/<domain>/actions.ts` — `"use server"` functions shaped `(prevState, formData) => Promise<ActionState>` for create/update (bind the id for update: `updateXAction.bind(null, id)`), and a plain `(id) => Promise<ActionState>` for delete (called directly from a client event handler via `useTransition`, not through `useActionState`).
- `lib/action-state.ts` defines the shared `ActionState = { status: "idle"|"success"|"error", message? }` shape returned by every action.
- `components/shared/use-action-toast.ts` — client hook that watches an `ActionState` and fires a `sonner` toast + optional callback (typically `() => setOpen(false)` to close the dialog) on success/error. Every form dialog wires this up.
- `components/shared/confirm-delete-button.tsx` — generic `AlertDialog`-wrapped delete trigger that calls a passed-in delete action and toasts the result.
- Validation lives in `lib/validation/*.schema.ts` (zod 4) and is the only place FormData gets parsed/coerced (e.g. `moneyField` in `lib/validation/money-field.ts` runs `parseTLToKurus` inside a zod `.transform`).
- All actual DB access goes through `lib/db/*.service.ts` — never call `prisma` directly from an action or component. `category.service.ts`'s `deleteCategory` is the reference example for the "block delete, explain why" pattern (`PROJECT_SPEC.md` §9): it throws a typed `CategoryInUseError` with a user-facing message rather than silently failing or cascading.
- **A prop passed into a still-open client dialog is not a stable "value before the edit" once the action calls `revalidatePath`.** `updateTransactionAction` calling `revalidatePath("/transactions")` makes Next.js re-render the parent Server Component (`TransactionsTable`) with fresh data *while the edit dialog is still mounted*, and pushes a **new** `transaction` prop into it as part of that same action round-trip — so by the time a success callback runs, comparing "current form state" against `transaction.<field>` deterministically compares the new value against itself (the prop has already moved). This exact bug shipped once in `transaction-form-dialog.tsx`'s "did the category change?" check (Faz 6) — a real browser click-through initially looked ambiguous only because of an unrelated test-script mistake layered on top, not because the underlying bug is intermittent; it reproduces on every edit. The fix: snapshot whatever "before" state you need into a `useRef` set only inside `onOpenChange` (dialog-open time), and compare/read against the ref, never against the prop, inside any success callback that fires after the mutation.

### Data model

`prisma/schema.prisma` is the source of truth; a few non-obvious decisions worth knowing before touching it:

- `Category` is self-referential (`parentId`) and shared between expense and income (`isIncome` flag) — there's no separate income-category table.
- `Transaction` and `MerchantRule` both carry **two** category FKs (`categoryId` for the top-level, `subCategoryId` for the child), per spec, rather than pointing only at a leaf category.
- `TransactionType` includes a fourth value, `PAYMENT`, beyond the spec's minimum `EXPENSE/INCOME/REFUND` — added deliberately (user-approved) to represent credit-card bill payments (e.g. "Ödeme - Enpara.com Cep Şubesi"), which are real lines in Enpara statements but aren't spending. Analytics/dashboard queries must filter these out of expense/income totals; forgetting the filter in a new query will silently inflate totals.
- `Statement.year`/`month` identify *which PDF* was imported (duplicate-import guard, spec §8) and are **independent** of which calendar month a `Transaction` belongs to — a single statement's period can span two calendar months (verified against the real reference PDF: a statement dated 05/08 covers transactions from 05/07 through 05/08). Monthly dashboard/analytics aggregation must always group by `Transaction.date`, never by the `Statement` it came from — **except** for statement-sourced installment continuation rows, see the next bullet for why that one case inverts the rule.
- **A taksitli (installment) transaction's `date` is the ORIGINAL purchase date, constant across every occurrence of that purchase — it is *not* the month that particular installment was billed.** Verified against real data: a Trendyol purchase dated 29/01/2026 has its 2nd installment appear in the March 2026 statement and its 3rd in the April 2026 statement, and **both rows carry `date = 2026-01-29`** (Enpara reprints the original purchase date on every installment line, per statement). Naively grouping by `Transaction.date` — the normal rule above — silently misattributes every installment after the first to whatever month/year the original purchase happened to fall in (in this case, a "January" that was never even imported). The fix, implemented once in `lib/db/transaction.service.ts`'s `getEffectiveMonth`/`transactionMonthFilter`: for a row with `source === "STATEMENT" && installmentTotal != null`, the true billing month is `Transaction.statement.year/month`, not `Transaction.date`. Every place that buckets transactions by month (`listTransactions`, `lib/analytics/monthly-summary.ts`, `lib/analytics/category-breakdown.ts`, `lib/installments/schedule.ts`) goes through one of these two helpers — don't reintroduce a raw `Transaction.date` range filter for a new month-bucketing query without checking whether installment rows need to flow through `getEffectiveMonth` first. Manually-entered installment transactions (`source === "MANUAL"`) are unaffected (the user picks the date per row directly), so the exception only applies to `STATEMENT`-sourced rows.
- `Installment` (the table) is deliberately left **unpopulated** — `lib/installments/schedule.ts`'s `buildInstallmentPlans` computes everything (grouping into one plan per purchase, real vs. missing vs. projected occurrences) on the fly from `Transaction` rows instead, keyed by `(normalizedMerchant, date, amount, installmentTotal)` — that grouping key relies on exactly the "date is constant per purchase" fact above. Writing to the `Installment` table would create a cache that goes stale every time a new statement is imported; recomputing is cheap (few taksit rows in practice) and always correct. Future installment months are a computed projection, never separate `Transaction` rows — don't double-count by materializing them.
- Duplicate protection is two-layered: `Statement` has a `@@unique([year, month])`, and `Transaction.fingerprint` (`lib/db/transaction.service.ts`'s `computeFingerprint`) hashes `date + normalizedMerchant + amount + installment` for same-statement duplicate detection — it intentionally does *not* dedupe two genuinely identical real purchases against each other.
- **Current credit-card debt ("Güncel Kart Borcu") is a derived value, not a stored column.** Enpara's own statement header prints a 6-number reconciliation formula (parsed into `ParsedStatement.reconciliation` by `lib/pdf/parse-statement.ts`): `previousBalance − payments + purchasesAndInstallments + cashAdvance + feesAndInterest = statement's ending debt`. Since `Statement.totalAmount` (as computed by `computeTotalAmount` in `statement.service.ts`) already equals `purchasesAndInstallments + feesAndInterest + cashAdvance` (every non-`PAYMENT` `EXPENSE`, minus `REFUND`), the formula collapses to `endingBalance = previousBalance + totalAmount − paymentsTotal`, where `paymentsTotal` is just `SUM(Transaction.amount) WHERE statementId = X AND type = "PAYMENT"` — no new field needed. `lib/db/statement.service.ts`'s `computeEndingBalance` implements this and `listStatementsWithBalances`/`getCurrentCardBalance` wrap it. Verified against the real 6-month dataset: every month's computed `endingBalance` equals the *next* month's stored `previousBalance` exactly (kuruş-for-kuruş, all 6 links), which is why this was implemented as a pure computation instead of a schema migration + backfill — the ground truth was already fully present in already-imported data. If a future statement is missing `previousBalance` (parser couldn't find the reconciliation line), `computeEndingBalance` returns `null` rather than guessing. **Never label this figure by `Statement.year`/`month`** ("Ağustos 2026 ekstresi itibarıyla") — a user caught this once: the label is technically about which PDF it is, but since that PDF's own content is mostly the *prior* calendar month (per the `Statement.year`/`month` bullet above), a month-name label reads as "this is your August situation" when it's really a snapshot dated early August of what's mostly July spending. `getCurrentCardBalance` returns `statementDate` (an exact `Date`) instead of `year`/`month` specifically so `CurrentDebtCard` can render an unambiguous full date ("05.08.2026 tarihli ekstreye göre") — don't swap that back to a month-name formatter.

### PDF parsing pipeline (`lib/pdf/`)

`extract-text.ts` (wraps `pdf-parse` v2's `PDFParse.getText()`) → `parse-statement.ts` (pulls statement date / next statement date / the 6-value reconciliation-formula line / transaction lines out of the raw text) → `normalize-transaction.ts` (regex-parses each transaction line, classifies `EXPENSE`/`REFUND`/`PAYMENT`, flags bank-fee lines, extracts installment tokens) → `validate.ts` (cross-checks parsed totals against the statement's own reconciliation numbers; returns warnings, never blocks import) → `parsers/enpara-parser.ts` (the `StatementParser` implementation `app/statements/actions.ts`'s `analyzeStatementAction` calls). `types.ts` defines the `StatementParser` interface so additional banks can be added later without touching this one.

Two things to know before editing this code:

1. **Line filtering is entirely "does the line start with `DD/MM/YYYY`?"** — every non-transaction line in a real Enpara statement (page headers, the repeated table header, the previous-balance carryover line, footer legal text, the interest-rate table) fails that test. This is deliberately simple; don't add more filtering heuristics unless a real counter-example shows up.
2. **Installment parsing is now verified against real data** (user provided 6 months of real statements, Mar–Aug 2026; see `tests/parser/fixtures/enpara-2026-03-installment-real.txt`). The real format turned out to differ from the original hypothetical fixture: `"TRENDYOL.COM ISTANBUL TR (849,00 TL) 2/3 283,00 TL"` — the parenthetical is the *total* purchase price (kept as part of the description, correctly, since raw text should be preserved), the trailing amount before `TL` is the *per-installment* charge, and `N/M` sits between them. `extractInstallmentToken`'s "N/M at the very end of the description" rule is purely structural (doesn't care what's inside the parenthetical), so it parsed this correctly with **zero code changes needed** — good validation that the original design generalized. See `tests/parser/fixtures/README.md` for the full comparison before changing installment-related parsing.

Test fixtures in `tests/parser/fixtures/` follow a strict real-vs-hypothetical labeling convention (`PROJECT_SPEC.md` §70 Kural 7: never silently assume PDF format without flagging it) — preserve that convention for any new fixture.

### Bank account statement pipeline (`lib/bank-account/`) — a SEPARATE PDF type from `lib/pdf/`, income-only by design

Enpara issues two structurally unrelated PDFs: the credit-card statement (`lib/pdf/`, above) and a monthly *hesap özeti* (checking-account statement — incoming transfers, outgoing EFTs, debit-card ("Encard") purchases, ATM withdrawals, and the outgoing "Enpara.com kredi kartı ödemesi" line that pays off the credit card). These are parsed and modeled completely separately; don't try to unify them.

- **This pipeline only ever writes `Income` rows — it NEVER touches `Transaction`.** An earlier version also saved outgoing lines as `Transaction` rows (`source: "BANK_ACCOUNT"`), which surfaced them in `/transactions` and pulled them into the dashboard's expense-side widgets (Toplam Harcama, Harcama Trendi, Kategori Dağılımı, Son İşlemler, Güncel Kart Borcu). The user explicitly reversed that: this data must affect **only** the Dashboard's "Toplam Gelir" figure (and, mechanically, Net Durum since that's `gelir − gider`) and live entirely inside `/income` — nowhere else. The `TransactionSource.BANK_ACCOUNT` enum value and `Transaction.accountStatementId` were added and then **removed again** in a follow-up migration once this was clarified; if you're tempted to re-add a way for this pipeline to produce a `Transaction`, don't — that reintroduces the exact thing that was reverted. `Income.accountStatementId` (nullable FK to `AccountStatement`) is the only cross-model link that remains.
- **Classification is a strict two-state system** (`lib/bank-account/classify.ts`'s `suggestLineClassification`, returns `"INCOME" | "EXCLUDED"` — see `lib/bank-account/types.ts`): every outgoing line (`isOutgoing: true` — EFT, Encard purchase, ATM withdrawal, credit-card payment, brokerage transfer, literally everything leaving the account) is suggested `EXCLUDED` unconditionally, no exceptions and no "gider" bucket at all. The only extra rule is for *incoming* lines: a transfer whose counterparty name matches the account holder's own name (self-transfer from the user's other account — e.g. "Gelen Transfer, Ahmet Yıldız, ...", the name extracted from the PDF's own "Ad soyad" field, never hardcoded) is also suggested `EXCLUDED`, since it's the user's own money moving, not real income. Every other incoming line defaults to `INCOME`. These are still just suggestions — the import preview lets the user flip any row before saving — but outgoing lines are shown in the preview (and used for the balance-chain validation below) purely for transparency; there is no way to persist one as anything other than excluded.
- **The PDF's own text layout is far messier than the credit-card statement's** (`lib/bank-account/parse-account-statement.ts`): dates are 2-digit years (`GG/AA/YY`, not 4), and a single transaction can span 1–4 physical lines depending on description length — the amount+balance pair may be appended to the last description line *or* sit entirely alone on its own line (verified against real data, see `tests/bank-account/fixtures/README.md`). The header info table (IBAN, account holder name, opening/closing balance, statement period) comes out of `pdf-parse` with its columns visually scrambled — don't try to parse it positionally; only two narrow, verified-stable regexes are used (the "Dönem sonu bakiyesi" block and the "gün sonu itibarıyla"/"Ad soyad" lines), and everything else about the header is intentionally left unparsed.
- **Validation** (`lib/bank-account/validate.ts`) replays the statement's own running balance (`opening balance + Σ signed amounts`) against each line's own "Bakiye" column and the final closing balance — same warn-don't-block philosophy as the credit-card side's reconciliation check, and still runs over *all* lines (including excluded/outgoing ones) since the balance chain needs every movement to tie out. All 6 of the user's real monthly statements (Şubat–Temmuz 2026) validated with **zero** warnings.
- **UI lives entirely inside `/income`** (`app/income/page.tsx` renders `AccountStatementUploadCard` + `AccountStatementsTable` below the existing manual-income section), **not** `/statements` — deliberate, user-confirmed placement, since `/statements` and `/transactions` are conceptually credit-card-only pages. The import flow (`app/income/account-actions.ts`'s `analyzeAccountStatementAction`/`saveAccountStatementImportAction`, `components/income/account-statement-*`, route `/income/import-account`) otherwise mirrors the credit-card one closely (upload → analyze → editable preview → save, `lib/statement-import/pending-account-upload.ts` parallels `pending-upload.ts`).

### Statement import flow (`app/statements/`, `components/statements/`)

The upload UI is split across two routes, and the split is bridged by an in-memory handoff rather than passing data through the URL or a DB write:

- `/statements` renders the drag & drop zone (spec §13). On file accept, it calls `setPendingStatementFile(file)` (`lib/statement-import/pending-upload.ts` — a plain module-level variable, not React state) and does a client-side `router.push("/statements/import")`. This works because Next.js App Router client navigations don't reset the JS runtime, so the module-scoped file survives the route change; it would **not** survive a hard reload.
- `/statements/import` (`components/statements/statement-import-flow.tsx`) calls `takePendingStatementFile()` on mount. If there's a pending file it runs analysis immediately; if the page was opened directly (no pending file — e.g. a bookmark or refresh), it falls back to rendering its own dropzone in place, so the route never dead-ends.
- Analysis and persistence are two separate Server Actions in `app/statements/actions.ts`: `analyzeStatementAction` (parses + validates + checks the duplicate-period guard, but never writes) returns the parsed data to the client for editing; `saveStatementImportAction` (called only when the user clicks "Ekstreyi Kaydet") re-checks the duplicate guard — since time has passed and the check needs to be race-safe — and is the only one that calls `createStatementWithTransactions`.
- Category assignment in the preview table is fully editable but seeded from `lib/categorization/engine.ts`'s suggestions (`analyzeStatementAction` calls `suggestCategoriesForTransactions` and attaches `suggestedCategoryId`/`suggestedSubCategoryId` to each row; `statement-import-flow.tsx` uses those as the row's initial `categoryId`/`subCategoryId`). `PAYMENT`-type rows (card bill payments) are excluded from category selection entirely and from the "kategori bekleyen" count, per the `TransactionType.PAYMENT` note above. Saving with unset categories is still allowed by design (spec §19 treats it as a reminder, not a gate) — plenty of rows legitimately have no confident suggestion (see the merchant normalization section below).

### Merchant normalization & categorization (`lib/merchants/`, `lib/categorization/`)

Two-layer system implementing spec §10 (merchant normalization) and §12 (category priority chain):

- **`lib/merchants/normalize.ts`** produces the canonical `normalizedMerchant` string stored on every `Transaction` (used by `app/transactions/actions.ts` and `lib/db/statement.service.ts` — never write raw `description` into that column). `stripKnownPrefixes` removes payment-processor noise (`GOOGLE *`, `IYZICO/`, `PAYTR ÖD/`, `PAYTR/`, `HEPSIPAY/`, `N KOLAY ODEM/` — real prefixes pulled from 6 months of the user's real statements, Mar–Aug 2026) to reveal the actual merchant underneath (e.g. `"GOOGLE *YouTube"` → `"YouTube"`), then `findKnownMerchant` (`known-merchants.ts`) canonicalizes well-known names. This file is pure and synchronous — no DB access.
- **`lib/categorization/engine.ts`** is the priority chain itself (spec §12: manual > MerchantRule > known merchant > pattern > AI > "Kategori seçilmedi"). "Manual" isn't code here — it's the invariant that the engine is only ever called to *suggest*, never to overwrite a category the user already set. The AI tier is intentionally absent (`lib/ai/` doesn't exist until Faz 12); the chain simply falls through to `null` when nothing matches, which the UI renders as "Kategori seçilmedi". `suggestCategoriesForTransactions` fetches `MerchantRule`s and the category tree **once** and reuses them across all transactions being suggested (not N+1 queries per row).
- **`known-merchants.ts` vs `pattern-rules.ts`**: known-merchants is exact/near-exact brand names (curated by hand); pattern-rules is broader keyword classes (market/yemek/ulaşım/fatura/vergi/hosting, plus the parser's `isBankFee` flag → Finans/Bankacılık). Both intentionally leave broad-catalog e-commerce (Amazon, Trendyol.com, Hepsiburada) **without** a category suggestion — normalizing the display name is safe, guessing "Teknoloji" or "Günlük Yaşam" for a site that sells everything is not. Category/subcategory references in both files are **plain strings matched against `prisma/seed.ts`'s actual category names** at suggestion time (`resolveCategoryByName` in `engine.ts`) — if the user renames or deletes a seeded category, matching rules for it just silently stop resolving (return `null`, fall through the chain) rather than crashing. Don't hardcode a category/subcategory name here without checking it actually exists in `prisma/seed.ts`.
- **Turkish case-folding for matching is its own trap, in two layers** — found via real reference-PDF data, not guessed: (1) JS's locale-independent `.toLowerCase()` turns Turkish capital İ into `"i" + a combining dot above (U+0307)`, silently breaking substring matches (`"Tİ CARET".toLowerCase()` does not contain `"ticaret"`) — `trLower` (`lib/merchants/text.ts`, `.toLocaleLowerCase("tr")`) fixes this. (2) But the real statement text is *inconsistent*: the same document has `"ELEKTRI"` in plain ASCII `I` right next to `"TİCARET"` in proper Turkish `İ`. `trLower` alone turns ASCII `"I"` into dotless `"ı"` (correct Turkish behavior), which then fails to match an `"elektrik"` keyword spelled with a regular `i`. **`matchFold`** (also in `text.ts`) is `trLower` plus folding `ı/ş/ç/ğ/ö/ü` to their ASCII equivalents — it's what every keyword-matching comparison in `known-merchants.ts`/`pattern-rules.ts`/`engine.ts` actually uses. `trLower` alone is only for standalone display-safe lowercasing; never use bare `.toLowerCase()` on Turkish merchant text anywhere in this codebase.
- **"Gelecekte de uygula?" (spec §11/§35)** lives in `transaction-form-dialog.tsx`, triggered only on a successful **edit** (not create) whose category actually changed. It fires a `sonner` toast with Evet/Hayır actions (not a blocking modal) — accepting calls **both** `createMerchantRuleAction` (`app/transactions/actions.ts`, upserts a `MerchantRule` keyed by `merchantPattern` — no DB-level unique constraint, only an index, so the service does a find-then-create/update) **and** `applyCategoryToMerchantAction`, which retroactively bulk-updates every *existing* `Transaction` sharing the same `normalizedMerchant` (excluding the row just edited) via `updateCategoryByMerchant` in `transaction.service.ts`. These are two independent, deliberately-combined effects: the rule only shapes future categorization suggestions (`lib/categorization/engine.ts`), it does not touch rows already in the DB — the retroactive bulk-update is what actually fixes already-imported transactions for the same merchant (e.g. correcting every past "AYŞE DEMİR" row in one click). See the "Server Actions / form pattern" section above for a real bug this surfaced around detecting "did the category change". A second, unrelated bulk path exists in `/transactions`: row checkboxes + `components/transactions/bulk-category-bar.tsx` call `bulkUpdateCategoryAction` to assign one category to an arbitrary multi-select of rows — that one is a manual, explicit selection, not merchant-driven.
- **Category deletion has a "move first" escape hatch.** `deleteCategoryAction` returns a `reason` (`"TRANSACTIONS" | "CHILDREN" | "OTHER"`) on `CategoryInUseError` now, not just a message — `CategoryDeleteButton` (`components/categories/`) uses `reason === "TRANSACTIONS"` to swap the confirm dialog for a target-category picker, then calls `moveCategoryTransactionsAndDeleteAction` → `moveCategoryTransactionsAndDelete` (`category.service.ts`), which reassigns `Transaction`/`MerchantRule`/`Budget` (and `Income`, main-category case only) rows to the target inside one `$transaction`, then deletes the source. Moving a **main** category clears `subCategoryId` on everything moved (the old subcategory doesn't exist under the new parent); moving a **sub**category sets both `categoryId` (to the target's parent) and `subCategoryId` (to the target). Only offered when `childCount === 0` for the source — a category that still has its own subcategories keeps the original blocking error, this flow doesn't attempt to move a whole subtree.
